# SSH владельца Pixel

> Переносимый runbook: адреса TEST-NET, имена и UID ниже — примеры,
> не описание вашей установки. Актуальные endpoints/ключи/результаты проверок
> храните в [приватном inventory](../PRIVATE-CONFIG.md), не в Git.


Это shell **Termux** (`u0_a123`), не root Android и не отдельная виртуальная машина. Владелец
может устанавливать пакеты Termux, передавать файлы и запускать свои сервисы.
Python 3.13.13, Git 2.54.0 и tmux 3.6b установлены; пакеты работающего
браузерного моста не обновлялись. Свободно около 82 GiB диска (не RAM).

## С этого Mac

```sh
ssh pixel                  # домашняя сеть, Pixel:8022
ssh pixel-remote           # через VPS, без статического внешнего IP дома
scp ./script.py pixel:services/
```

Настройки находятся в `config/ssh/pixel-owner.conf`, подключены **до** `Host *`.
Используется выбранный владельцем SSH-ключ из менеджера паролей. В
`~/.ssh/pixel-owner.pub` — только его публичная часть; отдельного незашифрованного
приватного ключа владельца на Mac не создавали. Host keys закреплены в
`~/.ssh/pixel-owner-known_hosts`; неизвестный/изменившийся ключ не принимается
автоматически. `ForwardAgent no` перекрывает глобальное значение dotfiles.

На другом компьютере нужны разрешённый владельцем ключ, клиентский config
и проверенные host keys. Не копировать private keys телефона и не применять
`StrictHostKeyChecking=no`. Панель владельца и SSH используют разные механизмы
входа; пароль noVNC для SSH не подходит.

Пример работы уже внутри Termux:

```sh
mkdir -p ~/services
cd ~/services
pkg install <нужный-пакет>
tmux new -As work
# Запустить свой скрипт. Отсоединиться: Ctrl-B, затем D.
# Вернуться после нового SSH-подключения: tmux attach -t work
```

tmux сохраняет процесс при отключении SSH, но не переживает остановку Termux
Android-ом или перезагрузку телефона. Для постоянного сервиса нужен отдельный
supervisor/boot entry. Не открывать прокси на `0.0.0.0` без аутентификации.

## Границы доступа

```
Mac --SSH--> Pixel:8022                    # внутри LAN
Pixel --исходящий SSH--> VPS:127.0.0.1:19223
Mac --pixel-owner-jump на VPS--> тот же туннель --> Pixel:8022
```

- Phone sshd слушает только IPv4 `127.0.0.1` и зарезервированный
  `192.0.2.116`, порт 8022. Пароль/keyboard-interactive запрещены.
- На VPS порт 19223 — **только loopback**, никаких новых WAN/роутерных портов.
- `pixel-owner-link` разрешён только remote forward на этот порт;
  `pixel-owner-jump` — только local/direct forward к этому порту. У обоих
  нет shell, TTY, agent/X11/Unix-socket forwarding. Ограничения проверяются
  через `sshd -T -C` перед выдачей ключей.
- Телефон хранит отдельные host-key и link-key в `~/pixel-owner/` (private).
  Приватные ключи не покидают телефон. На VPS только публичные ключи.
- SSH-forwarding в сервере телефона выключен. Это **не изоляция от владельца**:
  его shell имеет права Termux и доступ к его файлам/сетевым возможностям,
  включая ключи браузерной инфраструктуры. Поэтому этот доступ не выдаётся Hermes.
- Шифрование не защищает от компрометации VPS root: он управляет туннелями;
  проверка host key телефона сохраняет отдельную SSH-аутентификацию назначения.

## Автозапуск и восстановление

`~/.config/termux/boot/21-pixel-owner-ssh` запускает singleton supervisor,
отдельный от Hermes/Chrome/owner display lease. До появления LAN IP он не
стартует sshd (иначе можно незаметно остаться только с loopback listener).
Туннель включается только после подготовки VPS созданием
`~/pixel-owner/tunnel-enabled`. Удаление маркера запрещает **следующий** запуск,
но не завершает уже живой SSH процесс.

При завершении дочернего процесса — повтор с ограниченным backoff до 300 секунд.
SSH keepalive 15 секунд × 3; смена IP/обрыв сети допускает паузу восстановления.
`~/pixel-owner/status.json` содержит PID, число стартов, предыдущую ошибку и
признак доступности LAN-адреса. Это **не доказательство успешной аутентификации**.
Диагностика — `sshd.log` и `tunnel.log`, каждый не более примерно 2×64 KiB
с ротацией. Файлы private. Периодических неаутентифицированных SSH-проб нет:
они способны вызвать защиту OpenSSH от частых незавершённых подключений.

Реальное восстановление после перезагрузки Android ещё не проверялось:
телефон не перезагружали. Может понадобиться ручная разблокировка; Chrome/ADB
и захват VNC имеют дополнительные разрешения, которые один sshd не восстанавливает.

## Повторная установка / обслуживание

Source-only `install.py` запускается **внутри Termux**, с обязательным
`--inventory` (см. [приватную конфигурацию](../PRIVATE-CONFIG.md)) и путями к публичному
ключу владельца и заранее проверенному host key VPS. При существующем
`~/pixel-owner/` он останавливается, а не перезаписывает ключи.
`install_vps.py` — начальная установка двух новых учёток на VPS. Он также
отказывается перезаписывать существующие identities/config/порт. VPS-часть
должна быть готова **до** создания phone `tunnel-enabled`; иначе повторные
неуспешные входы могут временно закрыть SSH для общего домашнего адреса.
Не отключать защиту SSH для обхода такого сбоя.

Изменять только owner supervisor/listener, не Hermes/Incus и не весь Termux.
Перед обновлением проверить `sshd -t -f ~/pixel-owner/sshd_config`; сохранить
текущую owner SSH сессию до проверки новой. Ключи, private config и журналы
не публиковать в репозиторий. [DHCP и восстановление адреса](../DHCP.md).

## Проверено

- LAN SSH по ключу 1Password и закреплённому host key.
- Передача файла туда/обратно через SFTP с совпадением содержимого.
- Собственный тестовый Python HTTP сервис в tmux пережил отключение SSH;
  после проверки тестовый сервис, socket tmux и его файлы удалены.
- Unit/lifecycle tests покрывают отсутствие Wi-Fi → появление, падение
  собственного дочернего процесса → повторный запуск, диагностику и shutdown.
- Внешний канал и его recovery проверены отдельно от локального listener.

Внешний канал проверен 2026-09-12: `ssh pixel-remote` прошёл через
`pixel-owner-jump` → VPS loopback19223 → Termux `u0_a123`. Обе новые VPS-учётки
отказывают в shell; jump отказывает в другом destination и reverse-forward;
link отказывает в другом reverse listener и direct-forward. На VPS оба
телефонных порта (браузер19222 и owner19223) слушают только `127.0.0.1`.
Owner sshd после контролируемого завершения восстановился за 27 секунд,
новая аутентифицированная LAN-сессия прошла. Это не проверка перезагрузки Android.
Отдельное завершение owner tunnel восстановилось за 28 секунд; после него
новая сессия `ssh pixel-remote` также прошла. Браузерный мост не перезапускался.
После отключения диагностического Mac ADB снова прошли owner SSH через VPS и
CDP из контейнера Hermes. Отдельный финальный запрос самому Hermes использовал
настроенный browser tool: новая вкладка Example Domain, H1 и Android Chrome UA;
удаление только тестовой вкладки независимо подтверждено списком CDP targets.

Во время начальной установки преждевременные входы ещё не созданной учётки
вызвали Fail2ban для общего домашнего egress IP. Причина подтверждена журналом
VPS. Через существующий административный proxy-канал создана и проверена
учётка; снят **только этот ошибочный бан**, защита и остальные баны сохранены.
После этого обычный прямой SSH и браузерный туннель восстановились. Постоянные
SSH/browser-каналы через административный прокси не перенастраивались.

## Переносимый SSH client example

[client.example.conf](client.example.conf) содержит только TEST-NET адреса и
синтетический UID. Сформировать приватную копию с реальным LAN/VPS/UID и путём
к публичному ключу владельца; подготовить доверенные known_hosts отдельно.
Не ослаблять StrictHostKeyChecking, IdentitiesOnly или ForwardAgent.
Реальный `config/ssh/pixel-owner.conf` — локальный inventory, не публичный шаблон.
