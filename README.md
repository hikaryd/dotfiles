# Рабочее окружение

Dotfiles для macOS в стиле **Ayu Dark**: Ghostty, Nushell/zsh, Herdr/tmux,
AeroSpace/Rift, Neovim, Yazi, LazyGit и Pi Coding Agent.
Пакеты — [`Brewfile`](Brewfile), настройки — [`config/`](config/).

## Установка и проверка

Нужны Xcode Command Line Tools, Homebrew и Go 1.26+. Репозиторий — `~/dots`:

```sh
./install
./scripts/build-go-tools.sh       # пересобрать собственные Go-утилиты
make test                        # Go race/vet, Node и runner
```

Runtime — `tools/dots`, бинарник `dots-tools`; ссылки — в игнорируемом `build/bin/`.
Bash связывает установку и приложения; Python нужен стороннему Dotbot, не нашим командам.
Отдельные проверки: `make test-go`, `make test-node`, `make test-runner`.
Откат: `./uninstall --dry-run` для просмотра плана, затем `./uninstall`.
Без `--packages` пакеты Homebrew не удаляются; конфиги переносятся в бэкап.

### Уборка остатков старых установок

```sh
dots-tools setup cleanup             # только план, ничего не удаляет
dots-tools setup cleanup --apply     # удалить подтверждённые остатки
```

Уборка сверяется с `steps/*.yml`: снимает только битые ссылки на удалённые
исходники этого checkout, не трогая действующие managed links и `build/`.
Также удаляет Python bytecode без исходников, `.DS_Store`/`default.profraw`
в репозитории, старый кеш Spotify-toggle и суточные Atuin temp-файлы без живого
процесса-владельца. Пустые каталоги удаляются без рекурсии; ссылки на чужие
каталоги не обходятся. Приватные конфиги, подписки, токены, бэкапы, релизы,
виртуальные окружения и сторонние зависимости не очищаются. Файлы, изменившиеся
между планированием и удалением, сохраняются с ошибкой. Это не поиск «всего,
на что не нашёлся grep»: ручные команды и динамические импорты остаются.

## Ежедневные команды

```sh
dots                             # меню с поиском и цветами Ayu
dots help
dots menu --preview --plain       # предпросмотр без запуска действий
dots-tools palette --help
dots-vpn --help
kpstage get pods                  # context и namespace закреплены
kpdev-logs api                    # выбор pod и поток логов
kpprod-deploy-watch api           # read-only dashboard
kube-tools-help
```

Все собственные интерактивные команды используют один native Go UI: ↑/↓ или
Ctrl+N/Ctrl+P — выбор,
ввод — поиск, Ctrl+L — очистить, Enter — открыть, Esc/Ctrl+C — отмена.
Это относится и к tmux/sesh, gtab и `zi`: shell-обёртки вызывают `dots-tools ui`,
а не внешние picker’ы. Clipboard, prod-действия и uninstall требуют явного `yes`;
пустой Enter ничего не подтверждает. Пароли и URI подписок вводятся скрыто.
`dots status --interactive`: r/Enter — обновить, o — открыть, ↑↓/PgUp/PgDn — прокрутка,
Esc/q — выход, в том числе во время сбора снимка.
`NO_COLOR` отключает цвета; `--json` и pipe/export сохраняют обычный вывод.
Без терминала Kubernetes picker требует явный однозначный запрос, а не угадывает ресурс.
`fzf` оставлен для стороннего shell completion и стандартных Ctrl+T/Alt+C;
собственные меню от него не зависят.
[VPS и роутер](vpn/README.md) настраиваются отдельно, не обычным `./install`.

## Kubernetes: один переносимый бинарник

`dots-kube` работает отдельно от dotfiles, `private.zsh`, zsh и gum. Нужны только
`kubectl`, kubeconfig и, если они указаны в kubeconfig, внешние auth-плагины.
Встроенный Ayu-интерфейс одинаков в zsh, Nushell и других оболочках.
`dots-tools kube …` использует тот же модуль.

На новом компьютере передайте бинарник нужной платформы и безопасно получите
kubeconfig у администратора. Затем:

```sh
./dots-kube setup
# 1. Выбрать найденные файлы: Space — отметить, Ctrl+A — все, Ctrl+O — другая папка.
# 2. Для нужных окружений выбрать ФАЙЛ → КОНТЕКСТ → NAMESPACE.
# 3. Проверить общий план и выбрать «Сохранить настройки».
# Устанавливает команды в ~/.local/bin; исходные kubeconfig не меняет.
export PATH="$HOME/.local/bin:$PATH"  # добавьте в конфиг своей оболочки, если нужно

dots-kube config                  # источники, окружения, current-context; без секретов
dots-kube doctor                  # локальная диагностика, без запросов к кластеру
kpstage get pods
```

Явная настройка одного окружения, в том числе без терминала:

```sh
./dots-kube setup stage --kubeconfig /path/to/stage.yaml \
  --context existing-context --namespace application --yes
# Для отдельного prod-файла повторите setup prod --kubeconfig /path/to/prod.yaml …
# --import FILE отдельно импортирует предоставленный конфиг в локальное хранилище.
# --skip-aliases оставляет только настройку; --bin-dir DIR меняет каталог команд.
```

**Несколько файлов — нормальный сценарий.** Мастер ищет kubeconfig в `~/.kube/`,
в том числе в каталогах `config/` и `configs/`, а также в текущем `KUBECONFIG`.
Выбираются только отмеченные файлы; названия файлов не определяют окружение.
Для каждого окружения выбирается конкретный файл и context. При повторной настройке
выделяется сохранённая привязка именно этого окружения, не первый файл общего списка.
На шаге контекста Ctrl+O позволяет изменить выбранные файлы, Ctrl+L очищает поиск; счётчик показывает
число совпадений и общий размер списка. Поиск нового окружения начинается пустым.
На шаге namespace **Ctrl+O** получает реальный список из выбранного кластера:
это явный read-only запрос, после которого можно выбрать имя вместо ручного ввода.
Если RBAC запрещает `list namespaces` или подключение недоступно, остаётся ручной
ввод; ограничение показывается в мастере. Если namespace в context отсутствует,
мастер требует выбрать или указать его, не подставляя `default`. Повторная настройка того же подключения сохраняет ранее подтверждённый
namespace. Одинаковые имена
cluster/user/context в разных файлах не смешиваются: `kpstage` и `kpprod` имеют
раздельные цепочки загрузки. Если context и его cluster/user лежат в разных
файлах, стандартное объединение тоже поддерживается — только без конфликтов.

Выбор сохраняется в `${XDG_CONFIG_HOME:-~/.config}/dots-kube/sources.yaml` —
**пути и имя исходного context, без ключей**. Контексты `dots-dev`, `dots-stage`, `dots-preprod`,
`dots-prod` хранятся в соседнем каталоге `contexts/` и содержат лишь ссылки на
cluster/user и выбранный namespace. Исходные kubeconfig, включая read-only,
не переписываются. Менять или экспортировать `KUBECONFIG` после мастера не нужно.
Сохранённые привязки используются алиасами; явный `--kubeconfig FILE` в setup/config
важнее сохранённого выбора. До первой настройки используются стандартные
`KUBECONFIG` / `~/.kube/config`. Обычный `kubectl` и его `current-context` не меняются.

Esc возвращает на предыдущий шаг; до подтверждения ничего не записывается.
На узком экране длинное объяснение прокручивается PgUp/PgDn, кнопки остаются доступны.
Повторный setup допустим; невыбранные окружения сохраняют прежние настройки.
Запись собственных файлов — через приватные временные файлы и атомарную замену
каждого файла с проверкой внешних изменений.

`kdev/kstage/kpreprod/kprod`, `kp…` и суффиксы сами выбирают окружение **для
своего вызова**, не переключая обычный `kubectl` в других терминалах. Неизвестная
или конфликтующая привязка — ошибка, без угадывания окружений. Target/auth overrides
запрещены; аргументы контейнера после `--` сохранены. Изменения в prod требуют
`yes` в терминале или deliberate `KPROD_CONFIRMED=1`.
Старые `KUBE_<ENV>_KUBECONFIG/CONTEXT/NAMESPACE` больше не используются.
`kpstage config` показывает подключение stage, без запуска kubectl;
`kpstage setup` настраивает только stage. **`kpstage namespace`** получает список
namespace read-only запросом и позволяет изменить только namespace уже сохранённого
подключения, без повторного выбора файлов/context. Изменение сохраняется после
отдельного подтверждения; следующие `kpstage-*` используют его автоматически.
Для списка без изменения: `kpstage namespace --list --json`. `config --json` и `doctor --json --strict`
удобны для проверок в скриптах.

### Логи

`kpstage-logs-multi` без аргументов открывает список подов: ввод — поиск,
**Space/Tab** — отметить даже после поиска, **Ctrl+A** — все совпадения,
**Enter** — запустить отмеченные потоки. Отметки сохраняются при смене поиска.
Явный шаблон (`kpstage-logs-multi api error`) по-прежнему выбирает совпавшие поды
автоматически; второй аргумент — поиск в логах.

`kpstage-logs api` — отдельные записи: время, контейнер, полный текст,
визуальный разделитель. **Полная запись, включая все JSON-поля, видна по умолчанию.**
Длинные строки переносятся, а не молча обрезаются. **m** включает/выключает явный
краткий режим, показывающий только JSON `message`/`msg`/`event`.
В multi-view есть колонки RECEIVED/POD/CONTAINER/LEVEL/MESSAGE; ширина метаданных
адаптируется к терминалу, полные имена сохраняются, если помещаются.
Время RECEIVED — локальное время получения; исходные timestamps остаются в тексте.
Изменяются только нужные строки экрана, без очистки и прокрутки всего кадра;
поток не задаёт частоту перерисовки.

- **Space / p** — пауза или возврат к живому потоку. На паузе снимок не меняется;
  новые записи продолжают приниматься в ограниченный буфер.
- **↑↓ / j/k** — выбор записи; **Enter** — полный текст и форматированный JSON.
  Enter в LIVE сам ставит поток на паузу и открывает details; повторный Enter — назад.
- **m** — полный/краткий вид. Краткий вид не меняет сохранение и поиск.
- В деталях **↑↓ / PgUp / PgDn** — прокрутка, **←→** — соседняя запись.
- **/** — поиск, **f** — только совпадения, **c** — сброс; **Esc / q / Ctrl+C** — выход.

По умолчанию хранятся до 5000 записей и 32 MiB текста. Старые записи вытесняются;
счётчик виден в шапке. Пределы: `KUBE_MULTI_LOG_BUFFER`, `KUBE_LOG_MAX_BYTES`.
Очень большие записи ограничиваются только в UI; для полного исходного вывода —
`logs-save`. При выводе в pipe/файл TUI и цвета не добавляются; сохранённые логи
остаются исходными. Piped multi-logs сохраняют исходные байты, stderr отдельно
и код ошибки kubectl. `KUBE_LOG_DIR` меняет каталог сохранения.

### Перезапуск: pod или workload

```sh
kpstage-rollout-restart          # выбрать Deployment/StatefulSet/DaemonSet
kppreprod-rollout-restart api     # поиск в списке workloads
kpstage-deploy-watch             # смотреть ход обновления
```

`rollout-restart` позволяет отметить несколько workloads (Space/Tab, Ctrl+A)
и запускает `kubectl rollout restart` сразу для всех выбранных, **без ожидания
Ready каждого по очереди**. Контроллеры обновляются независимо по своим стратегиям;
`maxSurge`, `maxUnavailable`, StatefulSet partitions и прочие настройки не меняются.
Это не гарантия одновременной замены всех подов или отсутствия downtime:
Deployment с Recreate сохраняет Recreate, StatefulSet может обновляться по порядку.
Успех команды означает принятие запроса, а не завершение rollout.

Paused Deployment и OnDelete workloads отклоняются до отправки всех restart
запросов: одного изменения annotation недостаточно для автоматической замены подов.
В prod сохраняется обязательное подтверждение. Если kubectl возвращает ошибку,
часть запросов уже могла примениться — проверьте dashboard перед повтором.

`pod-restart` остаётся отдельной командой: удаление конкретных выбранных подов
последовательно с ожиданием Ready замены. Поведение этой команды не изменено.

## Лаунчер macOS

`Option+A` открывает Tinycast. В строке поиска доступны калькулятор и конвертация
валют, например `100 USD to EUR` или `100 USD to RUB`; курсы справочные.
Установщик назначает хоткей через `dots-tools setup tinycast-hotkey`;
если Tinycast уже запущен, перезапустите его после изменения.
Автозапуск включается в Tinycast → Settings → General → Launch at login.

## Управление Mac из Pi

Локальный MCP **Peekaboo** заменяет Orca для скриншотов, Accessibility, кликов,
ввода и управления окнами/меню. Homebrew-пакет и настройки обоих агентов

Общий skill `peekaboo` учит агентов проверять эффект действий новым снимком.

[Выбор альтернативы, настройка и результаты проверки](docs/desktop-mcp.md).
После применения настроек выполните `/reload` в Pi.

## Excalidraw MCP в Pi

`config/pi/mcp.json` подключает официальный удалённый сервер
`https://mcp.excalidraw.com/mcp` через `codemode`, без локальной сборки и ключей.
Применить: `./install -c steps/pi.yml`, затем `/reload` в Pi.
Проверить соединение: `pi mcp list`.

Pi не отображает интерактивный холст MCP Apps: доступны инструменты сервера,
но не встроенный графический редактор. Диаграмму можно сохранить в `.excalidraw`
и открыть в браузере. Содержимое диаграмм отправляется удалённому серверу;
секреты и закрытые данные в него не передавать.

`pi-apply` также исправляет манифест установленного `pi-supervisor@0.5.0`:
`typebox` переносится из `dependencies` в `peerDependencies`, зависимости от
модулей Pi получают диапазон `"*"`. Расширение остаётся включённым; исходный
манифест сохраняется в backup. Другие версии и пакеты не меняются. После
`pi update --extensions`, если предупреждение вернулось, повторить
`build/bin/dots-tools setup pi-apply` и `/reload`. Общие физические зависимости
npm не удаляются: ими могут пользоваться другие расширения.

## Прокси Pi и shell-команды

Pi обращается к моделям и внешним MCP через локальный VLESS-прокси.
Обёртка `pi()` автоматически вызывает `pi-proxy --ensure`: проверяет кеш или
выбирает самый быстрый доступный выход **вне РФ**. Страна определяется по
фактическому выходу через Cloudflare trace внутри туннеля, не по названию сервера.
Неизвестная страна тоже исключается; без проверенного маршрута Pi не запускается
напрямую. Корпоративный Nebula MCP обходит VLESS через `NO_PROXY` и routing xray.

Автовыбор проверяет до 4 изолированных туннелей параллельно, убирает дубли
конфигураций и сравнивает медиану 3 свежих запросов до OpenAI (CONNECT/TLS + ответ).
Рабочими считаются HTTP 200/401, но не 403, 429 или 5xx. Это задержка доступа к
API, не скорость генерации модели. Выбор кешируется на 30 минут; на каждом запуске
перепроверяются страна и OpenAI. Сбой или изменение подписки запускает новый поиск.
Проверки не отправляют API-ключи. Пока идёт замер, текущий xray продолжает работать;
смена победителя перезапускает общий прокси и может оборвать старые соединения.

```sh
pi-proxy --auto       # принудительно перемерить и выбрать быстрейший выход вне РФ
pi-proxy --status     # процесс и доступность OpenAI через выбранный выход
pi-proxy --update     # обновить подписку (следующий запуск учтёт изменения)
pi -p "ping"          # проверка/автовыбор прокси выполняется автоматически
```

`pi-proxy` — Go-контроллер бывшего codex-proxy; его также используют `jg` и
Spotifast. Приватные данные и кеш выбора лежат в `~/.config/xray-pi/` (0600).
Системные proxy-настройки и окружение родителя не меняются. `pi-apply` возвращает
`httpProxy: http://127.0.0.1:10810`, сохраняя явно настроенные личные прокси.
Строка Ayu показывает модель, TPS, контекст и расход текущей сессии Pi;
внешние CLI для лимитов подписок не требуются.

`shellCommandPrefix` в `config/pi/settings.json` дополнительно очищает
HTTP/WebSocket proxy env у инструмента `bash` и команд `!`/`!!`, в том числе
в старых процессах Pi. Это не затрагивает `KUBECONFIG`, `GITLAB_HOST` и `NO_PROXY`;
нужный отдельной команде прокси можно задать явно.

После применения `build/bin/dots-tools setup pi-apply` уже запущенный Pi нужно
перезапустить, чтобы обновить также proxy env для WebSocket и дочерних MCP.
В открытых bash/zsh обновите обёртку через `source ~/.config/shell/pi-proxy.sh`.
В Nushell мост zsh подхватывает обновлённую функцию при следующем вызове `pi`.

## Щадящий запуск pytest

Во всех обычных zsh-сессиях `PYTEST_XDIST_AUTO_NUM_WORKERS` по умолчанию равен `2`:
`pytest-xdist -n auto` не создаёт воркеры на все ядра. Настройка наследуется
дочерними процессами, включая `uv run pytest` и `python -m pytest`; явный `-n N`
или собственное значение переменной имеют приоритет. xdist не требуется для
проектов, которые его не используют, и параллельный запуск сам не включается.

Для фонового приоритета используйте обёртку:

```sh
pytest-safe -q                              # pytest из текущего PATH/venv
pytest-safe -- uv run pytest -n auto
pytest-safe -- python -m pytest -q
PYTEST_XDIST_AUTO_NUM_WORKERS=4 pytest-safe -- uv run pytest -n auto
```

На macOS обёртка использует `taskpolicy -b` и `nice -n 10`; без `taskpolicy` —
только `nice`. Это не жёсткая квота CPU и не ограничение потоков внутри тестов.
Обычные команды без `pytest-safe` автоматически получают только настройку xdist,
не фоновый приоритет. IDE, запущенные вне этой оболочки, и `zsh -f` не обязаны
читать `.zshenv`; сама обёртка задаёт значение по умолчанию и в этих случаях.
Для текущего терминала: `source ~/.zshenv; source "$DOTS_ROOT/config/zsh/commands.zsh"`.

## Jevgrep: семантический поиск для агентов

Используется официальный [dzhng/jevgrep](https://github.com/dzhng/jevgrep), CLI `jg` (Node.js 22+).
`./install -c steps/jevgrep.yml` устанавливает версию из `config/jevgrep/version`,
общий skill и инструкции Pi. Исходник skill взят
из тега `v0.8.0`; при обновлении CLI обновляйте и `config/jevgrep/skill/SKILL.md`.
Единые правила поиска — `config/jevgrep/instructions.md`, без отдельных профилей проектов.

```sh
jg auth                          # выбрать провайдера и сохранить ключ вне Git
jg doctor                        # проверить доступ синтетическим запросом
jg files ./src                   # оценить область без отправки исходников
jg "Где проверяется авторизация запросов?" ./src
~/dots/scripts/jg "Как работает поиск?" ./tools/dots  # прокси в shell агента
```

В zsh `jg` использует общий локальный прокси; standalone-обёртка `scripts/jg`
делает то же для shell-инструментов агентов. Поиск отправляет подходящие исходники
выбранному провайдеру: сужайте корень и используйте `--exclude` для закрытых путей.
Стандартные `.gitignore` / `.ignore` сохраняются. Результат — исходники в stdout;
индекс, Git-хуки, merge-драйверы и пересборка после редактирования не требуются.
После изменения глобальных инструкций выполните `/reload` в Pi.

## Приватные настройки

```sh
dots private init                # создать только отсутствующие шаблоны
dots private check               # проверить без вывода значений
```

`init` готовит два файла: приватные настройки оболочки и Git.
Существующие файлы не перезаписываются. `check` проверяет их права и известные
незаполненные шаблоны, не все внешние хранилища и не работоспособность ключей.
Заполняйте файлы редактором, не командами с паролями в истории терминала.

| Где | Что хранится |
| --- | --- |
| `~/.config/dots/private.zsh` | Личные алиасы, API-адреса и пути; пример — `config/zsh/private.example.zsh` |
| `~/.config/git/private.inc` | Имя/email Git и личные `maintenance.repo`; include фиксирован в общем Git-конфиге |
| `~/.pi/agent/` | `auth.json` и приватная история `sessions/`; вход — `/login` |
| `~/.config/jevgrep/credentials.json` | Провайдер и ключ Jevgrep; вход — `jg auth`, проверка — `jg doctor` |
| `~/.kube/`, `~/.ssh/` | Kubeconfig, SSH-настройки и проверенные `known_hosts`; ключи предпочтительно через менеджер паролей/SSH-агент |
| `~/.config/xray-pi/` | Приватная подписка и конфигурация прокси |

Учитываются `DOTS_PRIVATE_ZSH`/`XDG_CONFIG_HOME` и `PI_CODING_AGENT_DIR`.
Файлы с секретами — `600`, приватные каталоги — `700`; необязательные интеграции
можно не заполнять. Настройки телефона и других отдельных проектов ведутся в их репозиториях.

На новом компьютере восстановите только нужные файлы из защищённого хранилища
или через SSH с проверкой ключа, поправьте пути и выполните `dots private check`.
MCP для Pi применяются через `./install -c steps/pi.yml`; личные серверы сохраняются.
В OAuth-сервисы войдите заново, не копируйте автоматически токены,
cookies и сессии. Выполните `dots projects refresh`, чтобы пересобрать пути проектов.
Секреты и их бэкапы — вне Git; удаление из текущих файлов не очищает историю Git.
