# kubedesk: самостоятельный Kubernetes и metrics TUI

Дата: 2026-10-20. Статус: одобрен пользователем; готов к планированию реализации.
Независимая проверка полноты для планирования: существенных открытых вопросов нет.

## Зачем и что согласовано

Цель — дать другим командам существующие Kubernetes и metrics TUI без установки
личных dotfiles, Go и сборки из исходников. Пользователь получает готовый бинарник
и инструкцию, настраивает свои подключения и пользуется теми же возможностями.
Это выделение существующего продукта, а не переписывание интерфейса.

Пользователь выбрал:

- название `kubedesk`;
- публичный репозиторий `github.com/hikaryd/kubedesk` и бинарники в GitHub Releases;
- обязательную поддержку macOS;
- сохранение фиксированных окружений `dev/stage/preprod/prod`, без произвольных
  названий в первом релизе;
- самостоятельный проект, готовые релизные бинарники и описание настройки.

Предлагаемые инженерные решения ниже — решения автора дизайна, а не отдельные
пожелания пользователя. Их принятие входит в одобрение этого документа.

## Границы первого релиза

Одна репа и один Go-бинарник с главным меню Kubernetes и режимом метрик:

```sh
kubedesk
kubedesk setup
kubedesk config
kubedesk doctor
kubedesk metrics
kubedesk metrics init
kubedesk metrics check
kubedesk --version
```

Сохраняются текущие CLI, сочетания клавиш, офлайн-preview и короткие команды
`kpdev`, `kpstage`, `kppreprod`, `kpprod`, их варианты действий, `km`, `kma` и
`kube-*-watch` / `kube-pod-analyze`. Алиасы устанавливаются с согласия пользователя,
не обязательны для запуска основного бинарника. В неинтерактивном режиме запуск
без аргументов сохраняет текущую справку вместо попытки открыть TUI.

В перенос входят:

- мастер выбора kubeconfig → context → namespace, независимые файлы окружений;
- pods, одиночные/общие логи, поиск и сохранение логов, Job logs;
- наблюдение за rollout, CPU/RAM/процессами подов и локальная история;
- exec, scale, CronJob run, pod restart и workload rollout restart;
- Prometheus/VictoriaMetrics: обзор, графики, сервисы, HTTP-маршруты, разделы,
  детализация и пользовательские PromQL-запросы;
- прямое подключение метрик и управляемый `kubectl port-forward`;
- существующие unit-, CLI-, PTY- и regression-тесты этих возможностей.

Не входят: новый UI, новый metrics backend, произвольные окружения, перевод всего
UI, Windows, web-интерфейс, выделение универсальной TUI-библиотеки, kubectl/client-go
переписывание, Homebrew tap, автообновление, подпись/notarization Apple. В первый
релиз также не добавляется обещание поддержки любых exporter-ов из коробки.

## Исходная база и граница переноса

Разведка выполнена по исходникам dots, базовый HEAD:
`9a53c2063e6bced60949bbe2c6a8fd6798061009`. Перед переносом зафиксировать точный
исходный snapshot; новые изменения в этой области согласовать с ним.

| В dots | В kubedesk |
| --- | --- |
| `tools/dots/cmd/dots-kube/` | `cmd/kubedesk/` |
| `tools/dots/internal/kube/` со всеми подпакетами | `internal/kube/` |
| `tools/dots/internal/tui/` | `internal/tui/` |
| `tools/dots/internal/testpty/` | `internal/testpty/` |
| `scripts/build-kube-release.sh` | самостоятельный release build script |

Go module: `github.com/hikaryd/kubedesk`. Начальная версия toolchain — текущая
`go 1.26.0`; обновление Go/зависимостей не совмещается с переносом. `go mod tidy`
оставляет только используемые зависимости. Runtime не импортирует dots и не
ищет checkout. Сборка не требует соседнего dots, `go.work` или локального replace.

`internal/tui` и `internal/testpty` нужны другим инструментам dots, поэтому там
остаются. Их начальные копии в kubedesk развиваются независимо; это сознательная
альтернатива третьей общей репе. Единственным местом развития Kubernetes и
metrics продукта становится kubedesk, не dots.

Нужно адаптировать не только импорты и справку:

- `internal/kube/monitors.go`: повторный запуск того же исполняемого файла сейчас
  использует argv[0] `dots-tools`; дочерние watchers должны входить в собственный
  dispatcher kubedesk и корректно завершаться по сигналам;
- `internal/kube/aliases.go`: проверка принадлежности команд через Go build info
  должна знать новый module path и безопасно отличать старые собственные команды
  от чужих файлов/ссылок;
- shell-reload тест в `internal/kube/cli_test.go`, зависящий от
  `config/zsh/kube-tools.zsh`, остаётся интеграционным тестом dots, а не получает
  зависимость на этот файл в новом проекте;
- release ldflags устанавливают версию по новому import path;
- синтетические fixtures и PTY-тесты становятся автономными.

## Совместимость, настройки и безопасность

### Имена и файлы

Основное имя — `kubedesk`. `dots-kube` остаётся совместимым именем в интеграции
с dots; новым пользователям оно не нужно. Переменные `KUBE_*`, `KPROD_CONFIRMED`,
`NO_COLOR`, `KUBECONFIG` и поддерживаемые XDG-переменные сохраняют смысл.

Для новой установки:

- `${XDG_CONFIG_HOME:-~/.config}/kubedesk/sources.yaml` и соседний `contexts/`;
- `${XDG_CONFIG_HOME:-~/.config}/kubedesk/metrics.json`;
- если config-каталог находится в Git, приватный metrics inventory по умолчанию
  размещается в `${XDG_DATA_HOME:-~/.local/share}/kubedesk/metrics.json`.

Предложение автора для обновления существующей установки: без автоматического
копирования/удаления приватных файлов. Если новый конфиг отсутствует, подхватывается
существующий `dots-kube/sources.yaml`; contexts и последующие записи остаются рядом
с выбранным sources-файлом. Для metrics аналогично поддерживаются старые
`dots-kube/metrics.json` и `dots-private/metrics.json`. Явный `--config` метрик
имеет высший приоритет. При наличии нового файла он приоритетен; ошибка в нём
не замалчивается откатом к старому. Для каждого подсистемного конфига выбирается
один источник, без смешивания полей; порядок legacy metrics — сначала config,
затем data. Существующий небезопасный файл выдаёт ошибку, а не читается с ослабленной
проверкой. `init` никогда не перезаписывает выбранный существующий файл.

Документируются обнаружение старого конфига и ручной перенос. Стабильные внутренние
имена contexts `dots-dev/stage/preprod/prod` в первом релизе не переименовываются:
это идентификаторы совместимости, не зависимость от dots. Существующие generic
пути `kube-tools` для истории/списка workloads и `~/Documents/kube-logs` остаются,
как и их overrides; миграция данных не нужна.

### Kubernetes

Сохраняется pinning kubeconfig/context/namespace на каждый вызов; глобальный
`kubectl current-context` не переключается. Одинаковые имена context/cluster/user
в разных файлах окружений не объединяют учётные данные. В обычном setup исходные
kubeconfig не меняются; импорт остаётся явной операцией. Setup по умолчанию локален;
явное получение списка namespace выполняет только read-only запрос.

Подтверждение prod-операций и явный `KPROD_CONFIRMED=1` сохраняются. Отказ от
подтверждения, выход/отмена TUI, exit codes, stdin для exec, потоковый вывод и
недекорированные pipes/saved logs остаются частью контракта. Запрет опасных
target/auth overrides сохраняется.

Зависимости пользователя: `kubectl`, доступ к сети/кластеру и auth-плагины, которые
требует его kubeconfig. Сам kubeconfig и его exec-плагины должны быть доверенными.
Metrics через прямой URL не требует kubectl; port-forward требует.

### Метрики

Inventory и bearer-файл — вне Git, обычные файлы с `0600`/`0400`; symlink-файлы
не принимаются, проверки lexical/resolved родителей и Git worktree сохраняются.
`init` создаёт приватный пустой шаблон, `check` проверяет локально. Для профиля
задаётся ровно один источник: `url` или `port_forward`. Удалённый URL требует
HTTPS, HTTP разрешён для loopback. Не добавляются отключение TLS-проверки,
автоматическое использование shell HTTP proxy или логирование секретов.

В README нельзя обещать, что встроенные графики подходят любому кластеру:
описать ожидаемые метрики и labels, `request_metric`, `duration_metric`,
`route_duration_metric`, `status_label`, `route_label`, `namespace`, `service`,
а также `custom_only` и `queries` для иных схем. Отсутствующие данные остаются
неизвестными, а не нулём. Сохраняются ограничения ответов/рядов и трактовка
неполных данных и histogram bounds. Metrics режим read-only.

## Доставка и документация

Предложение автора: первый релиз `v0.1.0`, лицензия MIT для собственного кода
после проверки происхождения переносимых файлов. Лицензии зависимостей и чужие
copyright notices сохраняются; если права на публикацию конкретного материала
неясны, публикация блокируется до решения владельца.

Новая репа получает чистую историю с разрешённым snapshot, а не историю dotfiles.
В публикацию входят только код, обезличенные тестовые данные, документация и CI.
Реальные kubeconfig, inventory, токены, endpoints, логи, screenshots рабочих
кластеров, локальные пути пользователя и build output из dots не переносятся.
Перед первым push проверяются весь tracked snapshot, примеры и состав архивов.
Синтетические примеры используют example-домены и заведомо ненастоящие credentials.

Артефакты GitHub Release:

- `kubedesk_0.1.0_darwin_arm64.tar.gz`;
- `kubedesk_0.1.0_darwin_amd64.tar.gz`;
- `kubedesk_0.1.0_linux_arm64.tar.gz`;
- `kubedesk_0.1.0_linux_amd64.tar.gz`;
- `SHA256SUMS`.

Каждый архив содержит `kubedesk`, краткую инструкцию установки и лицензию; полная
документация находится в репе. Сборка `CGO_ENABLED=0`, `-trimpath`, версия связана
с тегом, `kubedesk --version` показывает версию и платформу. Бинарники не коммитятся
в Git. GitHub Actions проверяет изменения и собирает/публикует assets для
версионного тега только после успешных проверок. Workflow имеет `contents: write`
только у release job. SHA256 проверяет целостность загрузки, не заменяет подпись.

README и отдельный справочник настройки, на русском для первой аудитории:

1. Что делает инструмент, какие операции read-only, где требуется подтверждение.
2. Выбор macOS Apple Silicon/Intel или Linux, проверка SHA256, распаковка,
   установка в пользовательский bin и PATH. Для macOS — честное указание, что
   бинарники не подписаны/notarized; без инструкции отключать Gatekeeper глобально.
3. Предварительная установка kubectl/auth-плагинов и первый запуск Kubernetes.
4. Независимая настройка метрик: прямой HTTPS, port-forward, bearer-файл,
   built-in и custom-only профили, permissions и расположение вне Git.
5. Список настроек/алиасов, клавиш, диагностика распространённых ошибок,
   обновление/удаление, совместимость старых конфигов.
6. Как разработчику запускать тесты и собирать проект без dots.

Примеры в Git только синтетические; пользователь копирует их за пределы checkout,
устанавливает права и заполняет свои значения. Preview позволяет оценить оба TUI
без kubeconfig, kubectl и сети. Автоматические проверки примеров используют
временные приватные каталоги и fake backends, не боевые сервисы.

## Что остаётся в dots

Предложение автора: dots потребляет фиксированную версию GitHub Release, а не
собирает свою копию Kubernetes/metrics. Менять обе репы следует как одну миграцию,
но переключение dots — только после готовности и проверки нового релиза.

- Установщик скачивает архив для ОС/архитектуры и `SHA256SUMS`, проверяет сумму,
  затем атомарно заменяет принадлежащий ему бинарник. Ошибка сети/проверки не
  повреждает текущую установку. Версия закреплена явно, без плавающего `latest`.
- Старые entrypoints `dots-kube`, `dots-tools kube`, короткие команды и shell
  интеграция делегируют в установленный kubedesk, сохраняя argv, stdio, сигналы и
  exit status. При отсутствии бинарника — понятная ошибка с инструкцией установки,
  без скрытой загрузки при каждом запуске.
- Чужие файлы/ссылки не перезаписываются. Миграция распознаёт только прежние
  команды, принадлежащие dots, и новый kubedesk; наличие старого бинарника
  `dots-tools` не разрешает заменять основной многофункциональный runtime.
- `scripts/build-go-tools.sh` продолжает собирать остальные dots helpers, но
  перестаёт собирать Kubernetes. Его обычный build не становится скрытой сетевой
  установкой; установка kubedesk — явный шаг bootstrap/install.
- Продуктовые `internal/kube` и `cmd/dots-kube` удаляются из dots после проверки
  перехода; остаются только forwarding/integration code и его тесты. Общие TUI
  helpers остаются для других dots tools. Старый release script заменяется ссылкой
  на процесс релизов kubedesk, а не продолжает выпускать второй продукт.

Не переносить и не затрагивать незавершённые изменения `tools/task-tab-groups/`.
Работу по миграции dots изолировать от пользовательского dirty worktree.

## Условия готовности

1. Чистый clone kubedesk собирается и проходит `go test ./...`, `go test -race ./...`
   и `go vet ./...` без checkout dots и реального доступа к кластерам.
2. Существующее покрытие поведения перенесено; добавлены проверки нового имени,
   re-exec watchers, config selection/legacy fallback, безопасного alias install,
   сохранения prod guard и отсутствия внешних исходников в сборке.
3. CI запускает тесты на macOS и Linux. Для каждой из четырёх архитектур есть
   проверенная сборка; `--version`, `--help` и offline previews запускаются на
   доступных соответствующих runners. Cross-build не выдаётся за runtime-проверку:
   непроверенные runtime-комбинации явно указаны в release validation.
4. Все четыре архива и SHA256 опубликованы в `hikaryd/kubedesk` для `v0.1.0`;
   на Mac проверяется путь скачивание → checksum → запуск в временном HOME вне dots.
5. Kubernetes и metrics подключаются по документированным примерам в fake-backed
   тестах. Реальный smoke с частными подключениями возможен только отдельно и
   не является условием CI; диагностика не раскрывает их содержимое.
6. Обновление с текущих config/aliases не требует повторного ввода секретов;
   новые пользователи не зависят от файлов с именем dots. Привычные команды
   продолжают работать через интеграцию dots, без второй копии продуктового кода.
7. Публичный snapshot, история и release assets прошли проверку на приватные
   данные и на допустимость лицензирования.

## Что остаётся исполнителю

Точное разбиение модулей/тестов без изменения публичного поведения, реализация
тонкого forwarding и инсталлятора, перечень минимальных CI runners и организация
документации. Эти решения не должны менять описанные границы, безопасность,
совместимость или добавлять новые пользовательские возможности.

После одобрения документа составляется пошаговый implementation plan. До этого
не создаются новый проект/репозиторий, product code, релиз или публикация.
