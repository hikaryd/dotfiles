# Проверка обзора · 0.2.6

## Статус проверки

Локальные проверки пройдены. **Живое чтение подтверждено отдельно от фикстур**:
в 0.2.4 `GroupOverview.snapshot(true)` прочитал 6 групп рабочей сессии —
6/6 карточек Kaiten и 11/11 MR без ошибок. У всех карточек получена колонка;
3 карточки найдены по номеру задачи в MR, без вкладки Kaiten. GitLab вернул
7 успешных pipeline и 4 MR без pipeline. Учётные данные не извлекались.

В 0.2.5 `readStatusInTab(resource, true)` отдельно прочитал MR и одобрения всех
11 MR рабочей сессии: **8 `approved`, 3 `not-required`, ошибок нет**. У трёх MR
нет одобрений и обязательных правил, хотя API возвращает `approved: true`.
Проверено, что нормализатор не выдаёт это за пройденное ревью.
Однако 0.2.5 ещё учитывала сервисный аккаунт @SRV.SAMEDI.

В 0.2.6 повторено живое чтение всех 11 MR: **7 `approved`, 4 `not-required`,
ошибок нет**. Исключено 5 одобрений @SRV.SAMEDI: в одном MR оно было единственным,
в четырёх — вместе с одобрениями других пользователей. MR только с автоодобрением
не даёт зелёного статуса ни в нормализаторе, ни в сводке (`falseGreen: 0`).
Эти агрегаты получены из текущего production reader, не из фикстур.

Это проверка актуального контроллера и нормализаторов из временной страницы
расширения. Полный UI/переходы проверены в изолированном Brave; чтобы основной
service worker начал использовать новые файлы, расширение нужно перезагрузить.

## Воспроизведённые и исправленные дефекты

1. **Ложный выбор источника (0.2.1).** При `windowId === null` список окон визуально
   выбирал первое/активное окно, хотя группы ещё не загружались. Регрессионный тест
   сначала упал на этом состоянии. Теперь есть честный стартовый экран; выбор
   источника применяется сразу. Переключение окна сбрасывает поиск и фильтр,
   изменение через popup синхронизируется с обзором.
2. **Бесконечное «Проверяем статус…» (0.2.2).** Таймер внутри инъекции не ограничивал
   зависание самого renderer. Unit-тест сначала воспроизвёл незавершающийся snapshot.
   В настоящем Brave renderer карточки был остановлен через CDP `Debugger.pause`:
   прежнее поведение не публиковало даже готовые ответы остальных ресурсов.
   Теперь чтение одного ресурса ограничено 20 секундами **в service worker**, включая
   инъекцию, JSON и fallback. `tab.frozen` обрабатывается без инъекции. Незавершённая
   инъекция переиспользуется, а не дублируется на каждом обновлении; поздний ответ
   после таймаута не переписывает кэш незаметно.
3. **Блокировка всех результатов медленной вкладкой (0.2.2).** Список появляется
   независимо от API, а уже прочитанные статусы публикуются во время чтения остальных.
   Тест подтверждает 3 готовых MR при всё ещё остановленном renderer Kaiten, затем
   явную ошибку таймаута вместо бесконечного pending.
4. **Несоответствие компактному обзору (0.2.2).** Вместо развёрнутого перечня каждого
   ресурса — строка из четырёх колонок: задача, Kaiten, сводка MR, CI. Подробности
   раскрываются отдельно. Строка с тремя MR не выше 84 px на desktop; настройки
   доступа убраны в раскрываемый раздел. Сводка учитывает все MR, не только первый;
   частичные или устаревшие ответы не дают зелёный итог CI.
5. **Автообновление выключено, но события читают сайты (0.2.1).** События вкладок
   обновляют только список. Явный выбор источника и ручное обновление могут читать
   статусы. Устаревание данных продолжает отражаться без сетевых запросов.
6. **Успешный pipeline помечался частичным (0.2.3).** Цепочка API → нормализатор →
   сводка воспроизвела `success + head_pipeline:null` как «Частично / пропущен».
   Теперь MR без CI не входит в знаменатель pipeline: зелёный «✓ Пройден»,
   подпись «1 из 1 · 1 MR без CI». Настоящий `skipped` назван отдельно. Если CI нет
   вообще, неизвестен или устарел, зелёного успеха нет. Новый браузерный тест
   проверяет эту комбинацию на локальном HTTPS API.
7. **Выгруженные вкладки не читались (0.2.3).** Вместо обязательного открытия
   вкладки выполняется фоновый GET из service worker, с разрешением на сайт и
   cookies, приложенными самим браузером. Сохраняются проверка URL/окна/группы,
   запрет чтения после отзыва доступа, лимит 20 секунд и последние известные данные
   при ошибке. Общий дедлайн отменяет фоновый fetch и запрещает поздний fallback
   после завершения зависшей инъекции. Вкладки не открываются и не перезагружаются.
   Это не решает зависание
   renderer без флага `frozen` и не гарантирует принятие сессии корпоративным API.

8. **Неверный сессионный endpoint Kaiten (0.2.4).** В рабочем веб-клиенте обнаружен
   `/api/cards/:id`; запрос с обычной браузерной сессией вернул HTTP 200 и карточку
   с совпадающим ID. Ранее расширение обращалось к `/api/v1/cards/:id` и
   `/api/latest/cards/:id`, не соответствующим контракту сессионного веб-клиента.
   Регрессия сначала падала при рабочей веб-сессии и 401 у versioned API;
   теперь используется только `/api/cards/:id`. HTTP 401 не выдаётся за доказательство,
   что пользователь не вошёл на сайт; non-JSON отделён от ошибки авторизации.
9. **Карточка без вкладки Kaiten (0.2.4).** При отсутствии явной карточки в группе
   номер задачи из MR определяет URL Kaiten. Номер MR не используется, запрос
   перепроверяет актуальные вкладку/окно/группу/номер/разрешения. Чтение не создаёт
   вкладок. Явный клик переиспользует карточку либо открывает её в группе; двойной
   клик не создаёт дубликат. Разные номера задач не склеиваются. Живой запрос
   подтвердил 3 такие карточки, а браузерный HTTPS-тест — чтение и навигацию.

10. **Статус ревью (0.2.5).** Добавлена пятая колонка. Отдельный read-only GET
    `/approvals` отличает выполненные одобрения от отсутствующих обязательных
    правил и ожидания одобрений. Назначение ревьюера не считается одобрением.
    Старый формат без `approved` поддержан через явные счётчики правил; неизвестная
    или противоречивая схема не даёт зелёный статус. При 403 только у `/approvals`
    MR/CI остаются свежими, но прежнее успешное ревью не сохраняется. Проверены
    агрегация всех MR, истечение кэша, отдельные списки одобривших/назначенных,
    ошибки и безопасные диагностические счётчики.

11. **Автоодобрение считалось ревью (0.2.6).** Регрессия API → reader → сводка
    сначала воспроизвела зелёный статус от одного @SRV.SAMEDI. Теперь точный username
    исключён без учёта регистра; отображаемое имя и похожие username не используются
    для исключения. Счётчик и список одобривших не включают этот аккаунт, оставшееся
    обязательное количество пересчитывается без него. Наличие исключения объясняется
    в подробностях. Проверены bot-only с/без обязательных правил в обоих транспортах,
    bot+person, недостающий обязательный approval, дубликаты, регистр и неверная схема.
    Браузерный тест проверяет итоговые подписи, цвет и списки одобривших.

## Живая проверка и применение обновления

Предыдущие версии были проверены только на фикстурах: проблемы AppleScript/desktop
не позволяли подтвердить рабочий API. В 0.2.4 это ограничение снято отдельной
временной страницей расширения: она использовала те же производственные модули,
разрешения и браузерную сессию. Через заголовок страницы получены только агрегаты
(числа ресурсов, успешных чтений, колонок и коды ошибок), без полных ответов API.
Защитные настройки браузера не менялись, cookies и токены не извлекались.
Временная страница и её файлы удалены после проверки. Тем же способом в 0.2.5
проверены actual MR/approval ответы и новый нормализатор; в результат вынесены
только безопасные счётчики, без имён одобривших. Её файлы и вкладка также удалены.
В 0.2.6 таким же способом проверена фильтрация сервисного аккаунта на реальных
ответах; временные файлы и созданная для проверки вкладка удалены.

Чтобы применить файлы к основному service worker:

1. Перезагрузить расширение в `brave://extensions`, версия **0.2.6**.
2. Обновить страницу обзора и выбрать рабочее окно.
3. Нажать **Обновить** и дождаться завершения. Для проверенного набора вкладок
   ожидаются свежие данные **17 из 17**. При изменении состава групп число изменится.

Сверка реального UI после перезагрузки остаётся ручным шагом; успешное чтение
актуальным контроллером уже подтверждено, а не выводится из прохождения фикстур.
